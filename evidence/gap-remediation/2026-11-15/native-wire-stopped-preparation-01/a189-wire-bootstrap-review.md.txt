## One concrete blocker

The click loop sends Button1 down and later up, but `finally` only calls
`XCloseDisplay`. A fault or interruption between those two sends can leave
Button1 held on the owned Xvfb display. Add an unconditional Button1-up and
flush in `finally` before closing the X connection, preserving the original
exception if release itself fails. Root authorised a 104-line successor
cap for this safeguard. This is a neutral release, not an extra GUI action.

## Other checked boundaries

- `scripts/mac_runtime.py` records display-service `command` with `--`
  followed by `/usr/sbin/Xvfb :127 -screen 0 1024x768x24 -nolisten tcp
  -ac -noreset`; wrapper comparison matches that actual interface. It
  checks live service state, PID, UID, argv and saves display identity
  before later action.
- `native_emulator_readiness.py` disk receipt carries PID/start,
  `working_inode`, executable SHA and namespace inode; wrapper rechecks
  those against actual `/proc` and FD6, and checks FD16 if the lazy guest
  capture receipt exists. It does not read working-image bytes.
- The wrapper accepts only `capture`, `click`, `double-click` on :127 with
  output under O06/guiboot. Every input requires a fresh screenshot path
  and matching SHA within 30 seconds. The handoff requires human review
  of the visible target before using retained R04 coordinates, and stops
  on any unrecognised prompt or ambiguous target.
- Inputs cover the witnessed Launcher title activation, known HLserver19
  icon, one saver wake and visible Sounds Disabled OK. No Finder file
