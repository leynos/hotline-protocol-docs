# B102 read-only GAP-054 extfs missing-target feasibility plan

Date: 2026-11-14. Proposal only: no file creation/unlink, guest GUI, VM, protocol, oracle, or tracked edit. Use a **new** disposable runtime R and its exclusive `R/shared`, never retired R03, primary Files, an account, or a live disk image. Original criterion from frozen GAP-054 needs one genuine missing-target alias observation; B101 mapped the already met live/chain/name clauses.

## Source-supported pieces and unknowns

- `scripts/mac_runtime.py` creates a fresh `shared` directory and writes `extfs R/shared` into that VM's preferences. The network-isolated launcher uses `unshare --net`, not a mount namespace; the guest extfs and host see the same owned Unix tree. Pinned `extfs.cpp` roots the emulated volume at that path and calls host `stat(full_path)` during catalogue/info handling; `extfs_unix.cpp` stores Finder/resource sidecars under `.finf`/`.rsrc`. An unlink of a regular target leaf should therefore make fresh stat fail. This is a falsifiable source expectation, **not** proof that AliasManager cannot re-find a target by another identity or cached state.
- Handler 209 (`D-10017c10.c`, `AL-D-1002fb00.c`) creates a native `alis` resource and Finder alias flags from a resolved source; 205 creates a **directory**, not an alias. It is not yet proved that 209 can take an extfs source path through the server's Files-root resolver. The feasible route is Finder's Make Alias on an extfs file, then copy that alias into a new owned Files subdirectory while retaining its forks; this guest operation is a future separately reviewed UI step. Native 209 can subsequently make an alias-to-alias only if the existing source resolver positively accepts the copied alias. Do not assume it will.
- `AL-D-1002f600.c` and `AL-D-1002f310.c` show `ResolveAliasFile` or `FollowFinderAlias` depending on a global and a last argument zero. Neither retained body proves a no-UI locate policy. Native 206 classification of unresolved kind 6 is a source branch, not an expected result for this extfs case. The resolver can update/write the alias resource, so fork hashes require before/after snapshots.

## Conditional finite test, one target and at most six protocol cases

1. Prepare a fresh owner-free R from an immutable stopped base, fresh display/ports/captures/lease and a unique regular file `R/shared/<random-owned-leaf>` with known DATA bytes. Verify parent device/inode/owner, leaf regular/no symlink/nlink1, path exclusivity and SHA; optional `.finf`/`.rsrc` bytes are separate retained identities. Prove no same-name target exists in Files or another mounted location. Stage a fresh owned Files directory.
2. In the guest, positively show the extfs file on the Unix volume; use Finder Make Alias and copy the alias into only the new Files directory. Validate its HFS catalogue identity, Finder alias flag, `alis` ID0/resource fork and exact target alias chain. If guest creation/copy fails, stop: do not replace it with an unproved 209 extfs-source assumption.
3. While the target still exists, one native 200 and one 206 on the Files alias must show an entry and resolved target metadata/known length. If live resolution is absent, stop; this mechanism cannot test loss of a previously live target.
4. Close target handles and recheck exact parent/leaf identity immediately before a host `unlinkat`-style deletion of **only that basename** through an already opened, validated shared-directory FD. Refuse changed inode/device, symlink, hard link, directory, unexpected owner, wrong mount, or any path outside new R/shared. Retain the before hash/inode and successful unlink receipt; verify ENOENT for the exact leaf with `lstat`. Do not touch sidecars, Trash, aliases or disk bytes. This host unlink is future authority, not performed here.
5. Repeat bounded 200/206 on the same alias, then bounded 202 or 210 if 206 remains responsive. Capture complete requests/replies, control/data lifetimes and UI screenshot. If a locate dialog appears, retain it and allow at most one explicit Cancel of that exact dialog under the future packet; never choose another file or browse. Distinguish client/server timeout, cancellation, unresolved kind6, and positive new target resolution. No retry or guessed error text.
6. Quit/stop only owned guest, verify host leaf still absent, alias catalogue/forks and any `alis` mutation, original base and primary unchanged. Retain the raw extfs/guest/host evidence. A successful missing-target case is one where the **same** alias first resolved the known existing target, the exact extfs target was then positively absent, and a subsequent server lookup's bounded result is captured. It proves behaviour for an extfs-origin target; it does not prove an HFS-origin alias shares that policy.

## Decision gates

Source does not prove Finder can create/copy an extfs alias that native 206 resolves, nor that a host unlink is visible through every AliasManager cache, nor absence of a locate UI. These are experiment outcomes. Do not build the unlink step until the positive live 206 gate passes and a root-reviewed exact-object host unlink procedure exists. If a UI modal cannot be handled within the finite window, preserve partial evidence and stop. No extra volume, guest disk mount, original Files deletion or Trash emptying is needed for this conditional route.
