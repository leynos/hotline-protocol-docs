`Wire.poll` did not drop observed bytes; it preserved the late 302/301/ACK
in `frames` and the raw receive stream. The immediate exception path closed
observer before that fan-out could be observed. Thus this run proves a
**fixture wait failure under this process timing**, not a 304 rejection or
an ordinary per-pair latency distribution. Guest PCAP indices77/78 contain
the same 304 bytes at identical TCP sequence `3810816111`, a retransmission
rather than a second logical 304. The data cannot distinguish a
scheduled dispatcher tick, transient guest load, the retransmission, or the
observer FIN as the cause of the ~0.75s response.

## Bounded next design gate; no implementation or native START

A fixed >=0.8s per-pair wait would avoid this one cutoff, but 26 serial
pairs at 0.8s already consume >=20.8s before setup/jitter. Merely raising
0.55s while retaining the <=20 host-second trial guard is therefore an
incomplete fix. A proposed coordinator revision should send 304 then
same-socket500 for each icon2..27 without requiring both stream deliveries
*before sending the next pair*, drain all sockets concurrently, and verify
26 ordered subject301, 26 ordered observer301 and 26 numbered500 ACKs by
UID/icon/ID before ending the trial. It must retain the original counter
and global socket/byte/deadline guards, fail on duplicate/foreign frames,
and mark a >20s trial timing-invalid rather than stretch the native window.
It does not claim that pipelining is necessary or that the native server
will process all 26 within 20s.

First, parent-approved **synthetic process** rehearsal only: fresh fake
loopback server and proposed revised pair executor in an owned
namespace/managed unit, no emulator/native server. Model the exact
TRTP/login/roster/301/500
chain with a 0.75s first-response delay and alternate subject/observer
arrival order. Assert no observer FIN before all 26+26+26 obligations, all
raw tails retained, and a complete <=20s trial. A second slow schedule
(>=0.8s serial per pair) must fail as timing-invalid without relabeling
native rejection. Budget one synthetic 26-pair happy and one slow negative,
<=4 flows, <=60s wall/owned units, no native contact or changed routes.
If the process-level model cannot meet this or requires a new trust boundary,
stop and return timings/source proof. Only then consider a separately
approved disposable-native calibration or full C107 retry with new immutable
runtime, full preflight/captures/lease; do not reuse the failed lab or infer
native `GetDateTime` equivalence from host seconds. Existing C107 raw files
and failure label must remain unchanged.
