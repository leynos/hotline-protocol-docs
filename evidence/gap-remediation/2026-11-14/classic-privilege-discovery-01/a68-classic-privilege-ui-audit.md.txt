# A68: identified Classic client privilege UI, read-only inventory

## Exact input and method

- Read only the retained staged Classic candidate forks at canonical `state/mac-runtime/hotline-client-isolated-01/shared/HotlineClientCandidate/Hotline Client 1.9.2 Classic` and its adjacent `.rsrc/` fork. DATA is 1,410,822 bytes, SHA-256 `7f286e3f8941c2261fc9c32b2d1d03acef32bdea567362a1c64abd5d64fe5315`; RSRC is 729,097 bytes, SHA-256 `f762cfdedcc39758f841f720a4586dbbb88a7b74ec9e83db1793791b7c3f318b`. Both match `classic-account-constructors.md` and `state/delegation/b35-client-account-resource.json`. No live image was read.
- Archive label is “Hotline Client 1.9.2 Classic”; its `vers` resource says **1.9.1.0**. This is one hash-identified candidate, not a vendor-wide client profile. Existing `state/peer-resource-inventory-01/inventory.json` has 742 resource records and matches the exact RSRC SHA; its `MENU` 131 (`Hotline`, payload SHA `590aa0051a06b725539d09e06d16f35f16fe043e82d0ea2cbca35b17926f7d33`) contains New/Open/Administer Account actions. Its one `DLOG`/`DITL` pair is error dialog 9437, not an access editor. This resource inventory does not itself bind privilege checkboxes to bit indices.
- I parsed only exact Pascal-string regions in the retained DATA fork and compared the existing B35 literal inventory. No Ghidra or GUI query, app launch, network traffic, or source change was made.

## Positive labels; missing bit binding

- DATA `0x14d16e..0x14d458` is a contiguous run of 40 Pascal strings. Four are category headings (`File System Maintenance`, `User Maintenance`, `Messaging`, `Miscellaneous`); the others include account editor labels for file/folder actions, account create/delete/read/modify, messaging, news, private chat, name and agreement. A second near-duplicate run begins at `0x14f7e6`. The exact class-like literal `MyAdminEditUserWin` occurs at `0x14faf4`, shortly after that second run. Proximity makes an **account editor hypothesis**, not a proven code reference.
- Specific counted strings are `Can Get User Info` at `0x14d2f4`/`0x14f96c`, `Can Disconnect Users` at `0x14d306`/`0x14f97e`, `Cannot be Disconnected` at `0x14d31b`/`0x14f993`, `Can Send Messages` at `0x14d33c`/`0x14f9b4`, `Can Initiate Private Chat` at `0x14d3f0`/`0x14fa72`, `Can Use Any Name` at `0x14d434`/`0x14fab6`, and `Don't Show Agreement` at `0x14d445`/`0x14fac7`. These are client UI vocabulary, not established bitmap semantics.
- Frozen client `FUN_1000c210` (350), `FUN_1000c800` (353) and `FUN_1005b5b0` (349 object source) serialize an eight-byte access bitmap; the latter reads it at account-object offset `+4` (`classic-account-constructors.md:16-42`, corpus `client-account-constructors-01`). That is a positive **object-to-wire** edge. No retained source connects any of the above Pascal strings or editor controls to a specific mask/write into that `+4` bitmap. Alphabetical or displayed order is not bit order: the string run begins with download files/folders, upload files/folders, and upload anywhere rather than bit 0.
- In particular, this inventory establishes **no label→bit-18/19 or label→bit-41..63 edge**. It also does not prove those bits absent from the UI, reserved, or ignored by the server. The old protocol label “Send Private Message” at bit 19 is contradicted by native request-108 bit 40 (`D-1000f4e0.c`); `Can Send Messages` must not be silently assigned to bit 19 or 40. Resource strings at most reveal client intended wording after a code/control binding is proved; they cannot establish native enforcement.
