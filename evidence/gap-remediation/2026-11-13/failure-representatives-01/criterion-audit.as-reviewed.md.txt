## GAP-003 — error-code and failure-outcome registry

**Frozen question:** “Which statuses, field-100 forms and connection outcomes apply to each failure, including errors in operations without a normal ACK?” **Frozen criterion:** “Document a failure table and representative bytes for authentication, permission, missing-object, malformed-request and unsupported-operation cases.”

| Original clause | Current evidence | Audit |
| --- | --- | --- |
| Failure table | `error-outcomes.md`, “Wire status and failure classes”, gives trigger/path, native result and remaining boundary. `operation-contracts.md`, “Per-operation reply and fan-out map”, marks normal ACK, explicit-error branches and operations with no normal reply. | A table exists, but it is deliberately bounded; `error-outcomes.md` says the translation of thrown `SError` and some failure boundaries is unknown. |
| Authentication representative bytes | `evidence/gap-remediation/2026-11-12/native-core-01/old-password-rejected/report.json` and `early-login-and-errors/report.json` retain exact send/receive hex. `error-outcomes.md`, “Recorded representative native outcomes”, identifies status 1/text 100 and `Incorrect login.`; `native-wire-details.md`, “Credential bytes, lookup and account updates”, adds password contrasts. | Raw bytes exist in evidence; no authentication frame hex is rendered in the failure table. |
| Permission representative bytes | `native-core-01/low-privilege-and-missing-room/report.json` retains the permission-denied 348 exchange; `error-outcomes.md` cites it. Later exact status-1/text-100 cases are in `filesystem-and-board-contracts.md`, “Captured native folder creation and field-202 paths”, and its linked `native-mkdir-01` corpus. | Raw bytes exist, but are distributed across capture reports rather than a representative-byte table. |
| Missing-object representative bytes | `native-core-01/low-privilege-and-missing-room/report.json` (115) and `missing-file-info/report.json` (206), both cited in `error-outcomes.md`, retain exact hex. | Raw bytes exist; no missing-object frame hex is rendered in the failure table. |
| Malformed-request representative bytes and outcome | `native-core-01/malformed-zero-size/report.json` retains the sent zero-size frame and EOF observation. `error-outcomes.md` records closure without a numbered reply; `protocol.md`, “4 Reply semantics”, says there is no universal 111 before malformed closure. | Exact bytes and connection outcome are in the corpus, but no representative malformed frame/absence-of-reply row is rendered with the other cases. This one instance does not decide all malformed inputs. |
| Unsupported-operation representative bytes | `error-outcomes.md`, “Derived unknown-operation example”, renders a complete calculated 51-byte response layout (status 1, field 100, `Unknown transaction type!`) and expressly labels it derived. `native-core-01/early-login-and-errors/report.json` retains online unknown/replayed wire observations; `session-transport-contracts.md`, “Native envelope acceptance and emission”, records online types 0/FFFF. | This class has an inline representative layout, plus native raw evidence. Derived bytes must not be described as captured. |
| Original question: statuses and field-100 forms **for each failure** | The status-call review linked from `error-outcomes.md` finds 68 direct calls in 35 functions, all passing 1, with an explicit indirect/state-writing caveat. The same document separates internal domain/code from wire status and lists exception paths without a determined wire translation. | Not yet answered for each failure; the explicit exception/catch gap is substantive, not an optional expansion. |
| Original question: connection outcomes, including operations without normal ACK | `operation-contracts.md` identifies no-ACK operations 105, 113, 114, 116, 120 and 304; `error-outcomes.md` and `session-transport-contracts.md` distinguish direct error, silence and malformed closure. Native `native-banner-02`, `native-agreement-01`, `native-rooms-01` and `native-live-accounts-01` capture selected resets, quiet tails and FINs. | Selected outcomes are established, but the per-failure connection result for no-ACK paths and thrown exceptions is not complete. |

**Verdict:** Not a defensible closure candidate as currently documented. A failure table exists and each named class has raw evidence somewhere, but the criterion says to **document representative bytes** for all five; only the unsupported-operation example is laid out inline in the registry. More importantly, the frozen question asks for status/text/connection outcomes including no-ACK failures, while the current registry explicitly leaves exception translation and other failure boundaries unresolved. A minimal next step for the literal byte deliverable is a table linking or rendering one exact request/reply/closure witness per class, labelled captured versus derived. That alone would not settle the wider original question. Do not turn the later progress phrase “full operation-error taxonomy” into a new independent criterion; it describes the remaining breadth of this original question.

## GAP-071 — account field 111

**Frozen question:** “What is field 111's wire type, presence/default rule, stored meaning and effect on 350/353?” **Frozen criterion:** “Trace reads/storage/use of 111 and add an account field schema with absent, empty and representative-value fixtures.”

| Original clause | Current evidence | Audit |
| --- | --- | --- |
| Wire type | `account-attribute-trace.md`, “Positive field and storage evidence”, identifies byte-valued account TLV `0x6f`; `native-wire-details.md`, “Account record and field schema”, distinguishes wire TLV from internal 734-byte `UserData`. | Documented. No human semantic type follows from byte-valued wire data. |
| Presence/default on 350/353 | `account-attribute-trace.md` traces create `100146f0`, replacement `10014df0` and batch `10015500`: each copies field 111 into a freshly cleared record with a 64-byte cap. `native-wire-details.md` says absent/empty clears, and sparse 353 clears rather than preserving. | Bounded presence/default rule documented for these handlers. |
| Reads/storage/use trace | `account-attribute-trace.md` links the creator `100071a0`, writer `100075e0`, reader `100073c0`, ten direct callers, full-record preservation path `10007780`, and inspected forwarding/session/UI paths. `evidence/gap-remediation/2026-11-13/account-attribute-01/manifest.json` retains the read-only query corpus and checksum/verifier. | Positive storage and whole-record carriage shown. Direct-reader search is not exhaustive: copies, aliases, indexed and indirect reads remain possible. No semantic consumer is established. |
| Account field schema | `native-wire-details.md`, “Account record and field schema”, lists 111 length offset `0x254`, content `0x256`, 64-byte cap, and labels it opaque. `account-attribute-trace.md` adds the slot bounds and handling. | Documented as an opaque field, not as a known semantic attribute. |
| Absent, empty and representative-value fixtures | `native-core-01/account111-absent`, `account111-empty` and `account111-value` retain `plan.json`, `report.json` and 734-byte `UserData.bin` records: stored length 0/0/8 and `opaque-c` for the value. `native-account-update-01` adds 65-byte input clipped to 64 and sparse-clear replacement; the trace document links these. | Required fixture trio is present. Observed 352/348 omission is bounded output evidence, not proof of general non-use. |
| Original question: stored **meaning** and effect on 350/353 | `account-attribute-trace.md` explicitly says no positive human label or semantic consumer was found. Live attribute-only update shows unchanged effective identity/access in a measured window (`native-live-accounts-01`), while 350/353 storage/replace effects are established. | Stored bytes and replacement effect are known; human meaning and any behavioural effect beyond storage are unanswered. The no-match string search and absent direct dereference cannot prove “unused” or “reserved”. |

**Verdict:** The literal mechanical criterion (trace plus schema and fixture trio) has substantial, arguably complete bounded evidence. Closure of the **full frozen entry** is not defensible because its question explicitly asks for stored meaning and effect on 350/353. The documentation itself keeps the meaning opaque. The supervisor could record the mechanical criterion as satisfied while retaining the entry open for positive semantic consumer/UI/resource evidence, or separately decide that an opaque observed contract is sufficient for a revised scope. This audit makes no such scope decision and does not guess a field meaning.
