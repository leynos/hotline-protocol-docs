# C6 direct-ACK routing proposal (read-only)

Inspected canonical mxd `481294915b48f4db06943c8af86cf31b7e47597a` on 2026-11-13. `git status --short` showed only the pre-existing untracked `mxd.worktrees/`. No source edit, build, test, native traffic, or oracle lease was made. Leta was attempted first with a 15-second bound; its duplicate symbols under `mxd.worktrees/` required targeted source reads.

## Contract and observed mismatch

`hotline-protocol-docs/protocol.md:84-99,203-218` says native 1.9 **all numbered direct replies** use reply flag 1, wire type 0, copied request ID and status; numbered unsolicited notifications have reply flag 0 and their own type. `protocol.md:296-315` describes login ACK content. `mxd-reconciliation.md:63-69,110-114` records type-0 native ACK versus mxd's type-107 success predicate as unresolved GAP-085.

`src/transaction_type.rs:79-91` maps incoming 107 to logical `TransactionType::Login`. `src/wireframe/router.rs:58-108` retains the request header/kind, dispatches, and calls `compat_layer::finalize_reply` on normal command results. `src/login.rs:43-80` builds success and rejected-credentials replies through `reply_header`; `src/header_util.rs:17-37` currently copies request type 107 and ID. `src/wireframe/compat_layer.rs:146-168` augments this reply and serializes it; `src/transaction/frame.rs:204-213` writes the header unchanged. Thus the normal mxd login ACK **actually transmits type 107**, while 107 remains the correct request dispatch kind.

`src/wireframe/compat_policy/mod.rs:119-157` gates login extras on a successful reply whose header type is 107. Changing only the login handler or common reply constructor to type 0 would turn off 161/162 augmentation. Conversely, changing that predicate to accept type 0 without the original request kind would decorate successful nonlogin ACKs. The original request kind must be supplied to the gate.

## Complete producer/output trace

- `reply_header` has **14 production call sites across six modules**: `commands/handlers.rs` (5), `commands/support.rs` (1), `login.rs` (1), `news_handlers/mod.rs` (4), `presence.rs` (2), `wireframe/routes/reply_builder.rs` (1). All are direct reply constructors. `ReplyBuilder::error_bytes` also covers parse, command-parse, processing and missing-reply errors; it serializes via `Transaction::to_bytes`. Normal wireframe replies pass `finalize_reply` then `Transaction::to_bytes`; the legacy server passes handler replies through `TransactionWriter::write_transaction`. A login-only `finalize_reply` rewrite would leave nonlogin, error and legacy ACKs wrong.
- A **second public direct-reply constructor**, `wireframe/codec/mod.rs:89-107::HotlineTransaction::reply_from_params`, sets `is_reply=1` and also copies request type. Current production has no call to it; `codec/framed_tests.rs:52` uses it. The implementation packet should align this constructor too, and update its encoded-wire assertion at `framed_tests.rs:135`.
- `presence.rs:237-253::server_notification` constructs type 301/302 with `is_reply=0`; `wireframe/outbound.rs:134-143,242-254` serializes these with `Transaction::to_bytes`. `wireframe/outbound_tests.rs:125-137` already asserts a disconnect notification remains type 302. The notification path must preserve numbered type and marker 0.
- `FrameHeader::write_bytes` and `Transaction::to_bytes` are general codecs used for requests, replies and notifications; generic serialization should remain faithful to its supplied header. Normalize at direct-reply construction, not by silently rewriting arbitrary frames in low-level encoders. Separately, manually constructed reply frames may still encode arbitrary types, which is a codec capability rather than proof of a native server emission.

## One coherent correction for a separate approved implementation packet

At the **direct-reply construction boundary**, make `header_util::reply_header` produce type 0 while still copying request ID, setting reply flag 1 and preserving status/lengths. Align `HotlineTransaction::reply_from_params` with that rule. At the wireframe compatibility boundary, carry the **original request kind** already present in `finalize_reply(header, ...)` through `CompatibilityLayer::on_reply`, `LoginReplyAugmenter::augment`, and `ClientCompatibility::augment_login_reply`. Gate extras on `request kind == Login && reply.is_reply == 1 && reply.error == 0` (and direct reply type 0); leave peer identity, version/default-extra policy and server name unchanged. This replaces the unreliable use of reply wire type as a login discriminator. Request-ID correlation stays in the reply constructor; successful and failed login, nonlogin normal replies and router errors share type 0. Notifications remain independently constructed with marker 0 and numbered type.

This requires approximately **five production source files** (`header_util.rs`, `wireframe/codec/mod.rs`, `wireframe/compat_layer.rs`, `wireframe/login_reply_augmenter.rs`, `wireframe/compat_policy/mod.rs`) plus tests and the `header_util/kani.rs` harness. `ClientCompatibility::augment_login_reply` is currently public, so threading request kind changes its signature; that interface decision requires explicit approval. An alternative design that merely checks reply type 0 would lose the existing nonlogin safety gate and is not proposed. The full change exceeds a tiny one- or two-file login patch; C6 has no implementation approval.
