## Mechanism, not a flaky test

- `src/presence.rs:164-185::build_user_name_list_reply` deliberately encodes one repeated `FieldId::UserNameWithInfo` (300) entry per online user. With two users, the payload has two field-300 entries. It now uses `header_util::reply_header`, which correctly emits native direct ACK marker 1/type 0/request ID.
- `tests/wireframe_presence_bdd/wireframe_presence_support.rs:111-131::PresenceWorld::send` invokes the actual router, then `parse_transaction` on the returned bytes. `src/transaction/frame.rs:177-198::parse_transaction` calls `validate_payload`; the BDD step's later `decode_params` is never reached on the failed transaction. This is a production decoder/validator regression exposed by the test, not merely an assertion expecting old type 300.
- `src/transaction/params.rs:12-36::DuplicateContext::from_header` permits repeated field 300 only if `is_reply != 0 && header.ty == USER_NAME_LIST_ID (300)`. A native type-0 roster direct reply fails that condition and produces `DuplicateField(300)`. `decode_params` alone uses `DECODE_ONLY`, which allows repeated 300; the existing `presence_tests.rs::user_name_list_reply_contains_repeated_field_300_entries` calls that decoder and therefore missed the header-aware validation failure.
- `TransactionWriter::write_transaction` (`src/transaction/writer.rs:112-118`) and `TransactionReader::read_transaction` (`src/transaction/reader/mod.rs:120-142`) use the same validator; the legacy server would be unable to write this valid roster reply. `HotlineTransaction::from_parts`, `TryFrom<Transaction>` and `reply_from_params` (`src/wireframe/codec/mod.rs:110-184`) also use `validate_payload_parts`, so the Tokio codec constructor/conversion rejects the same valid direct reply. `HotlineFrameEncoder` reparses through `parse_transaction` before encoding (`src/wireframe/codec/frame.rs:100-109`). The low-level `HotlineCodec` encoder itself writes a caller-supplied header and is not the failing check.
- Targeted search found no other production payload validator condition on an echoed reply type. `HotlineFrameDecoder` maps incoming `header.ty` to a route ID (`codec/frame.rs:70-78`); a type-0 reply would map to fallback, but this is an inbound routing adapter with no demonstrated C7 server-output failure. It may need a separate bidirectional-client contract if mxd ever routes correlated replies as requests.
